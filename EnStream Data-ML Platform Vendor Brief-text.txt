3. Milestones and Scope (vendor vs EnStream)
3.1 Phase 1 — Batch Operationalized (target: end of June, owned by Data & AI team)
Customer value delivered: First production trust scores running on an ad-hoc batch cadence, each with a reason code, calibratable suspicion tier, and potential fraud flags. Manually triggered or simply scheduled.
The goal of this phase is to get the PoC out of notebooks and into something that runs reliably end-to-end on a schedule, even if the surrounding infrastructure is minimal, with the team's own data landing zone in place. This is our team proving the model works in a production-like setting before the vendor wraps a platform around it.
3.1.1 Shared Scope (vendor + Data & AI team)
● Incremental load from the IDV MySQL reporting DB into the Data & AI team's S3 (lead by Vendor):
o Extraction logic (incremental by timestamp, primary key watermark, or equivalent — full reload as a fallback)
o Land raw extracts into the bronze zone of the team's S3 in a stable file format (Parquet recommended) with partitioning by load date
o Idempotent re-runs — the same window can be reloaded without duplicating or corrupting downstream data
o Schema capture and basic schema-drift detection on extract (column added, removed, type changed)
o Run records: what was extracted, watermark advanced from/to, row counts, success/failure
3.1.2 Data & AI Team Scope
● Refactor PoC notebooks into a properly modularized repo — src layout, unit tests, semantic versioning
● Bronze-to-silver data cleaning and standardization
● Silver-to-gold transformation logic and feature definitions, codified, reading from the team's S3 bronze zone rather than directly from MySQL ● Reason code mapping v1 (owned by Product) ● Potential fraud flags v1(owned by Product)
6
● Suspicion tier calibration v1 against your weakly-labeled or expert-reviewed validation set
● Rule-based layer on top of model output, v1
● A runnable batch job — a single command or scheduled trigger that runs the incremental load, transforms bronze → silver → gold, scores, and writes outputs in the agreed format
● First-cut DQ checks at Bronze, Silver, Gold layers:
● Implemented as assertions or a lightweight check library inside the package itself, not yet a platform-level DQ framework
● Basic logging and run records (what ran, when, how many records, success/failure)
3.1.3 Vendor Scope
None in this phase. Vendor may shadow / observe / learn to prepare for Phase 2
3.1.4 Acceptance criteria
● Incremental load runs end-to-end from MySQL reporting DB into the team's S3 bronze zone, idempotent on re-run, with watermark advancement recorded
● Schema-drift detection on the extract surfaces changes in the source loudly, not silently
● Batch job runs end-to-end on production data and produces scores with reason codes and suspicion tiers, sourcing from the team's S3 rather than directly from MySQL
● DQ assertions pass on every run at both bronze, silver and gold layers; failures halt the job loudly rather than silently producing bad scores
● Score outputs reconcile to PoC outputs within agreed tolerance on a holdout set

3.4 Phase 3 — Real-time Inference (Interim via IDV) (target: end of August, vendor leads)
Customer value delivered: When an event occurs at the originating source system, affected identities get rescored within seconds. Decision-time and in-session use cases become possible. The Phase 2 batch process continues to run as the system-of-record reconciliation path; the real-time path is additive and authoritative for time-sensitive decisions.
8
Latency target: p95 under 2 seconds, p99 under 5 seconds, from event availability in IDV to score availability in consuming systems.
Application Engineering builds an application on top of the IDV MySQL reporting DB to capture events that occurred between the last batch run and the moment the API request arrives. This feeds an event index path on the data platform to refresh features and enable real-time inference — without rebuilding the underlying ingestion pipeline.

● Define the interface contract between Application Engineering's IDV query layer and the data platform's event index ingestion endpoint — covering payload schema, event typing, delivery guarantees, and error handling
● Agree on and document the latency budget split across the interim path: IDV query execution, event index write, feature recomputation, inference, score delivery
● Define the policy for events that are present in the event index but not yet reflected in the batch score: which use cases use the refreshed score vs. the last batch score, and how that is communicated to consuming systems
● Align on DQ ownership at the IDV boundary: who owns detection and triage of missing events, stale data, or IDV query failures

3.3.3 Vendor Scope
● Event index path: Build the continuous ingestion path that receives events from Application Engineering's IDV query layer, writes them to the event index, and sets dirty flags in the score cache for affected entities

● Selective recompute orchestrator: On API request arrival, check dirty flag state for the requested entity; if dirty, trigger incremental feature recomputation using the event index; if clean, return cached score
● Online feature store: Maintain incrementally updated feature state for entities flagged dirty; features updated from the event index, not recomputed from raw history on the hot path
● Online inference service: Model held in memory, no cold starts, horizontally scaled, returning score within the latency budget

● Low-latency score delivery: Sync API response or sub-second-lag topic for consuming systems

● Streaming DQ: Online observer checks for late arrivals, duplicate events, pipeline lag, and event index write failures; alerts on breach

3.4 Phase 4 — Real-Time Inference (target: end of December, vendor leads)
Customer value delivered: When an event occurs at the originating source system, affected identities get rescored within seconds. Decision-time and in-session use cases become possible. The Phase 2 batch process continues to run as the system-of-record reconciliation path; the real-time path is additive and authoritative for time-sensitive decisions. Plus more trust in our datasets because of DQ.
Latency target: p95 under 2 seconds, p99 under 5 seconds, from event occurrence at the originating source to score availability in consuming systems.
The architectural shift from earlier phases: Phase 1 and Phase 2 source data from the IDV MySQL reporting DB via incremental load into the team's S3. That path is too slow for sub-2-second targets. Phase 4 bypasses IDV entirely on the real-time path and ingests directly from originating source systems, processing events as they occur rather than after they've landed in a reporting DB.
Latency budget for p95 < 2 seconds:
● Source event capture and propagation to the streaming layer: 200–500 ms (requires direct integration with originating source, not a downstream DB)
● Trigger evaluation and entity identification: under 100 ms (precomputed trigger map, keyed lookups)
● Feature recomputation via online store with incremental aggregates: 200–600 ms (no recomputation from raw history; aggregates updated on event arrival)
● Model inference: under 200 ms (model in memory, long-running service, no cold starts)
● Rule layer and reason code mapping: under 100 ms
● Score delivery: 200–500 ms (sync API or low-lag topic)

3.5 Phase 5 — Continuous Everything: DataOps, MLOps, Continuous Retraining and Evaluation (longer-running, runs in parallel from Phase 2 onward)
Customer value delivered: Sustained quality. Drift caught early, deploys routine and safe, the system auditable for enterprise customers and compliance. Extending DQ upstream to source ingestion so issues are caught at the source rather than downstream.
This phase overlaps with Phases 2 and 3. The CI/CD foundations start during Phase 2. Continuous evaluation infra starts during Phase 2. Continuous retraining starts as soon as evaluation labels are trustworthy and provided on a regular cadence The source-ingestion DQ work starts during Phase 3 once the streaming pipeline exists to apply it to.
Workstream A (DataOps + source DQ) ensures the data the other workstreams depend on is trustworthy and that data issues are distinguishable from model issues.
Workstream B (MLOps) is the plumbing — it carries model artifacts from training through evaluation into production.
Workstream C (Continuous Retraining) produces candidate models on cadence and on demand. It cannot promote anything by itself.
Workstream D (Continuous Evaluation) is the judge. Nothing reaches production without passing it. The production model is also under its continuous watch.
