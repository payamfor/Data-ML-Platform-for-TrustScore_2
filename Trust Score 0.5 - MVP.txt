Trust Score 0.5 MVP ML Scope
1. Objective
Trust Score 0.5 will productionize EnStream’s unsupervised anomaly detection capability into a deployment-ready trust scoring framework that supports batch and real-time trust decisioning across the customer lifecycle. The system will produce a Trust Score (0–100), Low / Medium / High suspicion tiers, reason codes, and where applicable, flags indicating potential fraud type(s), using telco identity, behavioural, contextual, and relational signals. It must be dynamic, and explainable. The framework will support two operating modes:
•	a batch model framework for fraud operations and other offline customer problems, where feature subsetting is permitted to solve different customer-specific use cases related to fraud operations or adjudication prioritization
•	a real-time API model framework for onboarding and transaction monitoring, where a single standardized model is used respectively and feature subsetting is not supported
This approach allows EnStream to support customer-specific batch problem solving in earlier phases while converging to a more standardized and operationally simpler real-time model for API deployment.
2. Problem Framing
TS0.5 remains an anomaly detection problem, but the production scope must now explicitly account for two realities:
1.	Significant feature distribution drift exists across time, carrier conditions, partner populations, and operational contexts.
2.	Different use cases (onboarding, transaction monitoring, fraud operations) require different feature subsets, different baselines of “normal,” different thresholds, and different trade-offs between recall, friction, and false positives.
This means TS0.5 MVP should not assume one shared training distribution, one canonical feature vector, or one universal threshold policy. Instead, it must treat each use case as its own modeled environment with its own approved feature subset, preprocessing, calibration, and monitoring strategy given that labels and patterns vary, and that baseline behaviour shifts over time.
3.	Different deployment modes require different levels of model flexibility
For batch workloads, customer problems may differ materially, so Phases 1–2 will allow feature subsetting and use-case-specific model configurations to support different customer problems, baselines of normal behaviour, thresholds, and performance trade-offs.
For real-time API workloads, operational simplicity, consistency, latency, and maintainability are more important. Therefore, Phases 3–4 will use the same standardized model and will not support feature subsetting. In these phases, onboarding and transaction monitoring will rely on a common feature set, common preprocessing, and common model structure, with calibration and thresholding applied on top of that shared model as needed.
This means TS0.5 will not follow one single modeling strategy across all phases. Instead:
o	Batch phases optimize for flexibility and customer-specific problem solving
o	Real-time phases optimize for standardization, reuse, and operational scalability under API constraints
3. In Scope
3.1 In-Scope Phases
3.1.1 Phase 1 (Batch)
Phase 1 will move PoC tabular unsupervised models using Isolation Forest and KMeans to a production-ready batch-based MVP to generate a calibrated Trust Score, suspicion tiers, reason codes, and potential fraud-type flags for fraud operations and similar offline customer problems.
Because this phase is intended to solve different customer batch problems, feature subsetting is permitted. Separate feature subsets may be defined for different customer problems or batch use cases, with corresponding preprocessing, calibration, and threshold strategies.
In Scope:
•	productionize Isolation Forest and KMeans
•	define different feature subsets for different batch customer problems / use cases
•	establish use-case-specific preprocessing, score calibration, and suspicion tiers
•	generate Trust Score (0–100), Low / Medium / High tiers, reason codes, and flags indicating potential fraud type(s)
•	complete offline validation, threshold tuning, and deployment-ready model packaging
•	support at least one real customer batch workflow in controlled rollout mode
3.1.2 Phase 2 (Batch)
Phase 2 will industrialize Phase 1 by automating training, and scoring workflows for batch use cases. It will retain the same flexibility as Phase 1, meaning feature subsetting continues to be supported for different customer batch problems.
The primary output is a pipeline-driven ML operating layer that can repeatedly train, validate, and package batch Trust Score models for multiple customer-specific problem configurations.
In Scope:
•	automate model training workflows by batch use case / customer problem
•	automate batch scoring
•	orchestrate training, evaluation, and scoring with pipelines
•	automate feature-subset selection execution as defined by approved batch use-case configs
•	automate score calibration and threshold application where appropriate
•	automate artifact generation for model outputs and validation results
•	standardize release promotion from development to preproduction to production
3.1.3 Phase 3 (Real-time API)
Phase 3 will move from the batch MVP foundation to a production-ready real-time API MVP for onboarding, transaction monitoring, and fraud operations/adjudication APIs. Unlike the batch phases, Phase 3 will use a single standardized model for each API and will not support feature subsetting.
This phase is intended to support operationally consistent, low-latency API scoring for real-time customer decisions. The model will use one shared feature set, one standardized preprocessing flow, and one common model structure for supported API use cases. While the model itself will remain standardized, decision thresholds will be calibrated by use case and customer risk appetite to achieve the right balance between fraud risk mitigation and customer friction.
To support this, EnStream will use batch ground truth provided by customers — including known fraud and non-fraud outcomes — to automatically tune decisioning thresholds for real-time use cases. This calibration process will allow the same real-time model to be deployed consistently while tailoring decision sensitivity to the operational objectives of each customer, such as maximizing fraud catch rate, minimizing false positives, or reducing onboarding friction.
In Scope:
•	productionize a single standardized real-time tabular model for onboarding and transaction monitoring, and fraud operations/adjudication
•	define one approved real-time feature set and preprocessing flow
•	generate Trust Score (0–100), Low / Medium / High tiers, and reason codes
•	support threshold calibration by customer and use case based on risk appetite and friction tolerance
•	use customer batch ground truth to automatically tune decisioning thresholds
•	package the model for API-compatible inference
•	complete real-time deployment validation, latency validation, and threshold tuning
•	support at least one real customer real-time API workflow in controlled rollout mode
Out of Scope:
•	customer-specific feature subsetting
•	maintaining multiple real-time feature-set variants
3.1.4 Phase 4
Phase 4 adds full ML lifecycle control and ongoing model health management on top of the automated foundation built in Phase 3 to continuously evaluate model health, manage dependencies and artifacts, and retrain safely under drift. The primary output is a continuously managed ML system that can detect when the model is degrading, trace exactly what changed, and safely retrain or redeploy.
The purpose of this phase is to continuously evaluate the health of the shared real-time model, manage dependencies and artifacts, and retrain or recalibrate the model safely under drift while preserving one common model for all supported API use cases
In Scope:
•	establish continuous evaluation 
o	feature drift monitoring
o	score drift monitoring
o	anomaly-rate monitoring
o	reason-code distribution monitoring
o	use-case-specific performance monitoring
•	establish continuous retraining / recalibration 
o	scheduled retraining
o	trigger-based retraining under drift
o	recalibration-only path where needed
•	implement artifact and dependency tracking 
o	model artifacts
o	feature-subset configs
o	preprocessing dependencies
o	training metadata
o	evaluation outputs
•	implement CI/CD pipeline support 
o	validation gates before promotion
o	champion/challenger comparison
o	rollback support
•	define governance for model versioning, approval, and release traceability
3.1.5 Phase 5
Phase 5 will extend this framework with graph ML, such as a Graph Autoencoder, to improve detection of collective anomalies including fraud rings and shared infrastructure and it should repeat the same operating patterns established in phases 1 to 3. A comprehensive set of relational signals will be incorporated into tabular ML models.
In Scope:
•	build graph-based model inputs for customer, account, MSISDN, device, SIM, and related entities
•	develop graph ML models such as graph autoencoder or equivalent graph anomaly models
•	detect collective anomalies such as: 
o	fraud rings
o	mule networks
o	suspicious shared infrastructure
o	unusual neighbourhood patterns
•	fuse graph outputs with tabular Trust Score outputs where appropriate
•	generate graph-driven reason codes where feasible
3.2 In Scope ML Workstreams
3.2.1 Production-grade Tabular Anomaly Modeling Framework
The first phase of TS0.5 MVP will productionize the current tabular unsupervised ensemble model built on
•	Isolation Forest for detecting and scoring global anomalies and explainability
•	KMeans clustering for detecting and scoring local anomalies
The ML scope includes:
•	formalizing model inputs by use case
•	training one or more use-case-specific model variants
•	standardize ensemble logic across ML models
•	generating a single normalized trust score and suspicion band
•	generating reason codes and potential fraud flags
•	preserving extensibility for future semi-supervised ML models, and graph ML models and augmentation
3.2.2 Use-case-specific Model Design
Design and productionize separate model configurations for:
•	Onboarding / light KYC
•	Transaction monitoring
•	Fraud ops / adjudication
Each configuration must define:
•	target entity and scoring context
•	eligible feature subset
•	training population and exclusions
•	reason code policy
•	retraining cadence
•	acceptance metrics.
•	latency requirement
•	threshold strategy
•	review / escalation logic
3.2.3 Feature Selection and Model Input Governance
This includes:
•	define the approved model input schema
•	specifying mandatory vs optional features subset per use case
•	validate feature stability, leakage risk, sparsity, and carrier coverage
•	set feature quality gates for training and scoring
•	define fallback rules when input coverage is incomplete.
3.2.4 Drift-aware data preprocessing and normalization
Given significant feature distribution drift over time, preprocessing must be scoped as part of ML productionization.
This includes:
•	use-case-specific scaling / normalization rules
•	rolling reference windows for stable baseline estimation
•	treatment of seasonal and operational shifts
•	outlier clipping / winsorization policy where appropriate
•	handling changes in feature sparsity and missingness over time
•	use-case-specific data quality filters before scoring
3.2.5 Score Calibration and Suspicion Tiering
Raw anomaly scores are not sufficient for MVP. The system must output a calibrated decision-ready score.
ML scope includes:
•	mapping ML model outputs to a normalized Trust Score (0–100)
•	defining Low / Medium / High suspicion tiers
•	calibrating decision thresholds separately by each use case and customer based on their risk appetite
•	building score stability rules to reduce noisy oscillation
•	defining confidence bands or score quality flags when inputs are degraded
3.2.6 Explainability, Reason Codes and Attribute-Level Transparency
This includes:
•	defining model explanation logic for unsupervised ensemble outputs
•	reason-code generation from model outputs and dominant anomaly drivers
•	use-case-specific explanation templates
•	internal diagnostic explanation detail
•	customizer-facing explanation detail
•	mapping of model drivers to customer-consumable and business-readable terms
3.2.7 Offline Evaluation, Backtesting, and Production and Customer Deployment Testing
This should formalize metrics used in PoC (recall@k and precision@k when labels are available partially, KS statistics when labels are unavailable, robustness to drifts, and baseline lifts) into production acceptance tests and evaluation must be structured around per-use-case validation
Scope includes:
•	defining offline train/validation/test methodology
•	use-case-specific validation customer cohorts
•	time-based (weekly or monthly) backtesting and temporal holdouts to validate drift robustness
•	stability tests across time windows and customer populations
•	decision threshold stress testing by use case
•	false-positive review with customer SMEs
•	acceptance criteria for promotion from PoC to Deployment for customers
Minimum ML acceptance for MVP should include:
•	consistent lift over D4 or current integrity score baseline
•	stable score distributions over time
•	interpretable top drivers
•	acceptable latency at inference handoff
•	robust behaviour under missing or delayed inputs
3.2.8 Model packaging, deployment readiness, and runtime scoring logic
This includes:
•	training pipeline that is reproducible and parameterized
•	inference pipeline for batch and API-compatible scoring
•	model versioning and release management
•	artifact packaging and rollback support
•	deterministic preprocessing required at scoring time
•	score normalization consistency across releases
•	documentation of model inputs, outputs, thresholds, and reason codes
3.2.9 Monitoring and drift detection framework
This includes:
•	feature distribution drift metrics by use case
•	population stability monitoring by scoring cohort
•	score distribution monitoring
•	anomaly rate monitoring
•	reason-code distribution monitoring
•	detection of missing / delayed input features
•	post-launch performance review loops with fraud op
•	alert thresholds for retraining, recalibration, or rollback
3.2.10 Retraining and Recalibration Framework
TS0.5 MVP must include a defined operating model for updating models under drift.
This includes:
•	retraining triggers based on feature drift or score drift
•	recalibration-only path when score bands shift but model structure remains valid
•	full retraining path when feature relationships materially change
•	use-case-specific retraining frequency
•	shadow validation before promotion
•	champion-challenger comparisons before release
3.2.11 Responsible and controlled rollout
TS0.5 MVPis unsupervised and designed as a risk signal rather than a final verdict, the scope should explicitly support human-in-the-loop rollout
This includes:
•	rollout mode definition: 
o	shadow
o	advisory
o	controlled decision support
•	analyst review workflow support
•	score confidence flags
•	rollback and safe-disable logic for bad model behaviours

6. Data Requirements
6.1 Phase 1
Phase 1 is a batch-first MVP for Trust Score 0.5. Its purpose is to prove that EnStream can transform raw telco and EnStream interaction data into a production-ready batch trust score for fraud operations and similar offline use cases, using a minimal but reliable set of features and training data. For Phase 1, the emphasis is not model sophistication; it is having enough clean, well-structured, historically consistent data to generate batch features, train a basic unsupervised model, validate outputs offline, and support at least one real customer batch workflow.
All data should be stored in raw file format in S3 bucket for bronze layer, and iceberg format in S3 tables in S3 buckets for silver and gold layers.

fraud labels from telcos and banks
Telcos and banks provide confirmed fraud outcomes as batch labels. These are fraud investigations take days to weeks to resolve but they are the ground truth against which the unsupervised models are evaluated offline.
These labels arrive with a lag of 3-90 days after the actual fraud event (time for investigation, customer dispute resolution, and internal review). The label ingestion pipeline normalizes them into a canonical label schema and joins them to the historical anomaly scores that were active at the time of the fraud event, enabling retrospective model evaluation.

TransUnion (TU) PortPS provides a real-time event feed of all number porting requests and completions across all Canadian carriers. This is an industry-wide data source that provides cross-carrier visibility.
This event type is uniquely valuable because it captures inter-carrier movement that no single telco sees in full (beyond Rogers, Telus and Bell). A fraudster porting a number from Bell to Rogers generates events in both carriers' feeds plus the MNO porting feed, and the porting feed is the only source that ties both sides together.
Note: PortPS does not give visibility into whether the number is currently active with the unsupported carriers and the number can be recycled with unsupported carrier between porting as well.

6.2 Data Pipeline
6.2.1 Ingestion Architecture
The ingestion step will use AWS Glue as the primary batch data-processing framework. For source datasets stored in a MySQL database in another AWS sub-account, Glue will connect over approved cross-account networking and IAM access, and will extract data incrementally using:
•	Glue job bookmarks to persist ingestion state between runs
•	bounded execution windows to restrict each run to a specific lower and upper bound
•	source-side predicates based on a stable incremental key
This pattern is required so batch ingestion remains scalable, restartable, and safe for reprocessing. Bookmarks will be used to avoid rereading already-processed records, while bounded execution will support deterministic recovery, controlled backfills, and reruns for specific historical intervals.
TU PortPS must be ingested through a separate API-pull workflow because it is an external porting source, not part of the cross-account MySQL extraction path.
The TU pull workflow must:
•	call the TU PortPS API on a scheduled batch cadence
•	request records incrementally using a persisted watermark or cursor
•	land the raw request / response payload in bronze
•	log request metadata, response status, record counts, and pull window in _metadata
Raw inputs include
•	account_changes_batch
•	audit_trail_services_3
•	device_lookup_batch
•	partner_configuration
•	TU API response
6.2.2 Bronze Layer
The bronze layer is the immutable raw landing zone. All extracted or received source data must be written in raw file form to S3. Bronze must preserve the source payload as received, including raw schemas, timestamps, and source-delivery boundaries. It is the replay point for debugging, reprocessing, and audit.
6.2.3 Silver Layer
The silver layer is the conformed data layer. Glue jobs must transform bronze data into typed, normalized, deduplicated Iceberg tables in S3 silver. The silver layer must be implemented as partitioned Iceberg tables in S3, versioned by dataset and event date as already specified in the requirements
6.2.4 Gold Layer
The gold pipeline must continue to build:
•	account_changes_canonical_events
•	msisdn_lifecycle
•	msisdn_lifecycle_account_mapping
•	msisdn_lifecycle_account_customer_mapping
•	normalized_casnonical_events
The lineage (mapping) construction logic must now be updated to make TU a first-class incremental correction source, not just an optional enrichment:
•	inserting new lifecycle boundaries when TU confirms a port-in or port-out event
•	revising inferred lifecycle start or end timestamps when TU is more authoritative than telco-only inference
•	updating mno_port_ind, temporary_pn_ind, and inference flags where appropriate
•	preserving versioned history rather than silently overwriting lineage state
•	updating msisdn-account mapping where TU changes account continuity assumptions
•	updating msisdn-account-customer mapping where porting connects or separates customer histories across carriers
•	normalized canonical events so TU porting is represented as part of the event stream consumed by feature generation
Unresolved lifecycle handling and TU confidence check
After lifecycle and account/customer lineage construction, the pipeline must identify records that cannot be confidently attached to an MSISDN lifecycle using telco and EnStream data alone. These unresolved records should be placed into a lineage resolution queue.
For records in this queue, the pipeline must apply the following rule:
•	if the number’s unresolved state is explained only by a recent port-out within the last 30 days, the pipeline must use TU PortPS data to verify the current port status before permitting Trust Score calculation
This TU verification step is required to increase confidence that the number has truly exited the prior supported-carrier lifecycle and is not being mis-scored because the lifecycle appears open, broken, or ambiguously terminated. It is especially important because the requirements already note that TU gives cross-carrier visibility but does not guarantee visibility into whether the number remains active with unsupported carriers and that numbers can be recycled with unsupported carriers between porting events.
The output of this resolution step should be one of:
•	resolved and attached to lifecycleT
•	verified recent port-out, lifecycle closed with TU support
•	still unresolved after TU verification
Only the first two should proceed to standard TS calculation. Records still unresolved after TU verification should be flagged for exclusion, deferred scoring, or low-confidence handling according to downstream scoring policy
Feature Generation
Feature generation remains downstream of lineage and normalized canonical events.
The feature jobs must consume TU-updated lineage and TU-normalized porting events so that:
•	tenure reflects corrected ownership continuity
•	phone-number-change (excluding temporary phone numbers) and MNO-port sequences are correct
•	customer, account, and MSISDN snapshots reflect cross-carrier lineage as accurately as possible
•	recent-port-out unresolved numbers are not misrepresented as valid scoring subjects
This is consistent with the current feature pipeline, which depends on lineage-derived phone number change and MNO port events and computes features relative to point-in-time customer, account, and MSISDN snapshots.
6.2.5 Orchestration Workflow
1.	extract incremental MySQL source data using Glue bookmarks and bounded execution
2.	pull TU PortPS data via API using stored watermark / cursor
3.	land raw MySQL and TU outputs in bronze
4.	build conformed silver tables and run DQ checks
5.	build canonical events
6.	update MSISDN lifecycle incrementally
7.	update account and customer lineage incrementally using TU where applicable
8.	run unresolved-lifecycle detection
9.	finalize lineage confidence state
10.	generate normalized canonical events
11.	generate feature sets
12.	assemble training / eval datasets
13.	hand off to the modeling pipeline
14.	monitor outputs
7. Model Requirements
7.1 Phase 1
7.1.1 ML Problem Statement
TS0.5 Batch Phase 1 is framed as an unsupervised anomaly detection problem.
The model is intended to identify phone numbers, accounts, customers or related identities whose behavioural, contextual, and simple relational signals deviate materially from what “normal” looks like for the relevant customer problem. The output is not a final fraud verdict; it is a risk signal used to prioritize fraud investigation, adjudication, case review or to proactively monitor risks in existing customer base. This is consistent with EnStream’s own framing that Trust Score should identify deviations from baseline and support fraud operations, onboarding, and transaction monitoring with a calibrated Trust Score, suspicion tiers, reason codes, and associated potential fraud flags
Required Inputs
The model framework should support feature subsetting for different customer problems
This means:
•	the underlying model class remains the same: Ensemble of Isolation Forest + KMeans
•	but the feature subset, preprocessing rules, score calibration, and thresholds could differ by batch customer problem
•	each batch customer problem may therefore produce its own model configuration even if the model family remains unchanged. It must define: 
o	problem definition
o	target scoring entity
o	approved feature subset
o	exclusion rules
o	calibration rules
o	threshold rules
o	acceptance metrics
Required outputs
The model must output:
•	Trust Score (0–100)
•	Calibratable Low / Medium / High suspicion tier
•	Reason codes (top features explained using shap)
•	Where appropriate, potential fraud-type flags for fraud operations workflows (mapped manually by product SME)

7.1.7 Modeling pipeline
The pipeline must support manual retraining and batch inference, not online learning or automatic retraining. It must also preserve the Phase 1 modeling requirement that the underlying model family remains an Isolation Forest + KMeans ensemble, while allowing feature subsetting by batch customer problem.
7.1.7.1 Inputs
The modeling pipeline must consume:
•	versioned gold feature sets
•	problem-specific training / validation / evaluation snapshots
•	the selected feature subset for the target batch customer problem
•	calibration and threshold configuration
•	optional fraud / non-fraud retrospective labels for offline evaluation
•	lineage and dataset manifests for reproducibility
7.1.7.2 Pipeline Stages
Step 1 — Load training snapshot
Read the versioned training snapshot from S3 gold and validate that:
•	the expected feature subset is present
•	schema matches spec.json
•	dataset version and snapshot date are resolved
•	required metadata and manifests are available
Step 2 — Apply preprocessing
Apply the approved preprocessing package for the batch customer problem, including:
•	imputation
•	feature subsetting rules
•	scaling / normalization where required
•	PCA or other dimensionality reduction where configured for KMeans preprocessing
•	outlier handling rules
•	feature exclusion rules
•	data quality filters
•	feature selection rules: 
o	Ensemble of IF-Permutation, SPEC, DIFFI, NDFS
o	Reduce highly correlated features (keep only <0.8)
Data preprocessing must be deterministic, parameterized, and tied to the selected problem configuration
Step 3.1 — Train Isolation Forest
Train the Isolation Forest component using the approved hyperparameter configuration. The current requirements specify Isolation Forest as the global anomaly detector in the Phase 1 classical ensemble, with tunable parameters
Step 3.2 — Train KMeans
Train the KMeans component for behavioural segmentation and local anomaly detection using the selected problem-specific feature subset and preprocessing output. The current requirements specify KMeans as the local/segment-based anomaly component, with cluster count justified using silhouette coefficient and elbow test
Step 4 — Score and combine
Generate:
•	Isolation Forest anomaly outputs
•	KMeans segment-relative anomaly outputs
•	combined ensemble score
•	normalized Trust Score (0–100) 
o	the higher the score the most trustworthy/least anomalous the mobile identity is
•	Low / Medium / High suspicion tier
•	reason-code candidates
•	potential fraud-type flags where enabled
Step 5 — Offline evaluation
Run the required evaluation suite:
•	recall@k where labels exist
•	precision@k where labels exist
•	KS statistics or equivalent anomaly-separation metric where labels are sparse or partial
•	baseline lift vs D4 / current integrity score where applicable
•	score stability across time windows
•	robustness under missing inputs
•	error analysis by carrier and customer problem
Step 6 — Explainability generation
Generate model explainability outputs for the release candidate, including:
•	reason-code mappings
•	top-driver outputs
•	SHAP-based artifacts where supported
•	plots and diagnostic summaries
Step 7 — Persist artifacts and register experiment
Log the full run to MLflow and persist all outputs to the required S3 structure
Step 8 — Manual promotion
Phase 1 promotion is manual. A release candidate is promoted only after:
•	evaluation review
•	error analysis review
•	reason-code review
•	threshold review
•	signoff for controlled batch rollout
The Phase 1 is manual-retraining / controlled-rollout posture and with the broader requirement for human-in-the-loop rollout and release control.
Step 9 - Batch inference
The batch inference pipeline should reuse the same preprocessing and scoring logic as training-time evaluation, but applied to the target production population.
The inference flow should be:
1.	load the approved model version from S3
2.	load the matching feature-set version for the inference date
3.	validate schema and feature coverage
4.	apply deterministic preprocessing
5.	run Isolation Forest and KMeans scoring
6.	compute ensemble Trust Score, tier, reason codes, and flags
7.	write predictions to: 
o	outputs/predictions/model=<name>/version=<id>/dt=YYYY-MM-DD/
8.	write monitoring outputs to: 
o	outputs/monitoring/model=<name>/version=<id>/dt=YYYY-MM-DD/

Required evaluation dimensions
Evaluation must include:
•	recall@k where labels exist
•	precision@k where labels exist
•	KS statistics or equivalent anomaly separation metric where labels are sparse or partial
•	baseline lift vs current integrity score / D4 where applicable
•	score distribution stability across time
•	robustness under missing or delayed inputs
•	interpretability of top drivers and reason codes
•	batch inference runtime at target volume

•	stable scoring behaviour across time windows
•	operationally interpretable outputs for fraud operations
